# Uptime

**Мониторинг доступности веб-сайтов и HTTP-сервисов.**

Uptime автоматически проверяет ресурсы по расписанию, определяет доступность и измеряет время отклика. Сервис помогает обнаруживать ошибки подключения, превышение времени ожидания и неуспешные HTTP-ответы.

Для каждого ресурса задаются собственные интервал проверок и таймаут. Настройки сохраняются в PostgreSQL, а мониторинг восстанавливается после перезапуска приложения.

## Возможности

- **HTTP(S)-мониторинг** — периодические GET-запросы к сайтам и API.
- **Контроль доступности** — ответы `2xx` считаются успешными; остальные статусы и сетевые ошибки фиксируются как неуспешные проверки.
- **Время отклика** — измерение длительности получения HTTP-ответа.
- **Настройка проверок** — индивидуальные интервалы и таймауты для каждого монитора.
- **REST API** — создание мониторов и получение списка ресурсов.
- **Постоянное хранение** — сохранение конфигурации в PostgreSQL.
- **Корректная остановка** — отмена активных проверок и ожидание завершения фоновых задач.

Результаты проверок на текущем этапе выводятся в логи приложения.

## Технологии

| Компонент | Технология |
|---|---|
| Приложение и HTTP API | Go, `net/http` |
| База данных | PostgreSQL |
| Подключение к БД | pgx, pgxpool |
| Генерация кода для SQL-запросов | sqlc |
| Миграции | goose |
| Запуск окружения | Docker Compose |
| Автоматизация | Makefile, GitHub Actions |

## Архитектура

HTTP-обработчики принимают запросы и передают операции хранения репозиторию. Репозиторий использует запросы, сгенерированные sqlc, для работы с PostgreSQL.

Планировщик получает конфигурацию мониторов из базы и организует фоновые проверки. HTTP-проверка определяет успешность ответа, время начала и длительность выполнения.

```text
cmd/uptime/                     Точка входа и жизненный цикл приложения
internal/api/                   HTTP-обработчики и контракты API
internal/monitor/               Модель монитора и HTTP-проверки
internal/scheduler/             Планирование и выполнение проверок
internal/infra/postgres/        Подключение к PostgreSQL
  repository/                   Репозитории
  migrations/                   SQL-миграции
  queries/                      SQL-запросы для sqlc
  sqlc/                         Сгенерированный код доступа к данным
```

## Запуск

### Требования

- Docker с поддержкой Docker Compose.
- Go — для локальной разработки и запуска тестов.
- goose — для применения миграций.
- sqlc — для генерации кода после изменения SQL-запросов.

### Конфигурация

Создайте `.env` в корне проекта и задайте параметры PostgreSQL:

```dotenv
POSTGRES_USER=uptime
POSTGRES_PASSWORD=change_me
POSTGRES_DB=uptimedb
POSTGRES_HOST=127.0.0.1
POSTGRES_PORT=5432
```

Для подключения приложение использует переменную `DATABASE_URL`.

При запуске приложения внутри Compose адрес базы — имя сервиса `postgres`:

```dotenv
DATABASE_URL=postgres://uptime:change_me@postgres:5432/uptimedb?sslmode=disable
```

При запуске приложения непосредственно на компьютере используется опубликованный адрес базы:

```dotenv
DATABASE_URL=postgres://uptime:change_me@127.0.0.1:5432/uptimedb?sslmode=disable
```

`sslmode=disable` используется для локального окружения.

### Подготовка базы

Запустите PostgreSQL:

```bash
docker compose up -d --wait postgres
```

Примените миграции:

```bash
make migrate-up
```

Параметры подключения должны быть доступны команде через окружение или настройки Makefile. Миграции выполняются отдельно от запуска приложения.

### Запуск приложения

```bash
docker compose up --build -d app
```

При публикации порта `9000:8080` API доступен по адресу:

```text
http://localhost:9000
```

Просмотр логов:

```bash
docker compose logs -f app
```

Остановка окружения:

```bash
docker compose down
```

## Разработка

Сборка всех пакетов:

```bash
go build ./...
```

Форматирование:

```bash
go fmt ./... 
```

Статический анализ:

```bash
go vet ./...
golangci-lint run
```

После изменения SQL-запросов или схемы обновите сгенерированный код:

```bash
make generate
```

Файлы в `internal/infra/postgres/sqlc` генерируются автоматически и не редактируются вручную.

## Тестирование

Тесты HTTP-проверок используют локальный тестовый сервер и проверяют успешные ответы, таймауты и отмену запросов.

Интеграционные тесты репозитория работают с отдельной PostgreSQL-базой. Для локального запуска используются переменные:

```dotenv
POSTGRES_TEST_HOST=127.0.0.1
POSTGRES_TEST_PORT=5433
POSTGRES_TEST_USER=uptime_test
POSTGRES_TEST_PASSWORD=test_only
POSTGRES_TEST_DB=uptime_test
```

Запуск тестового PostgreSQL, применение миграций и проверка репозитория:

```bash
make test-integration-local
```

После подготовки тестовой базы и переменных окружения можно выполнить все тесты:

```bash
go test ./...
```

Проверка гонок данных:

```bash
go test -race ./...
```

Детектор гонок требует включённого CGO и доступного C-компилятора.

## Миграции

Миграции хранятся в `internal/infra/postgres/migrations` и управляются goose.

Создание новой миграции:

```bash
goose -dir internal/infra/postgres/migrations create migration_name sql
```

Применение:

```bash
make migrate-up
```

Уже применённые миграции не изменяются: изменения схемы оформляются отдельными миграциями.
